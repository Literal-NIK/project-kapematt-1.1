# Kapematt Technical Architecture Guide

This document is the engineering handoff for Project Kapematt. It describes the code that exists today, how requests move through the application, and how to change the project without breaking its runtime, route tree, data contracts, security boundaries, or user-facing behavior.

It is written for a developer who may join the project at any stage and needs a reliable map before editing code.

## 1. What the project is

Kapematt is a server-rendered React catalog for a single-location supermarket. It supports:

- Retail product discovery, department browsing, offers, stock labels and product details.
- Wholesale browsing with case sizes, units, minimum order quantities and quote-oriented pages.
- Store information, bakery and deli content, contact forms and a custom cake inquiry.
- Responsive UI, route metadata, not-found handling and server-side error pages.

It is deliberately **not** an online shop yet. There is no cart, checkout, payment, delivery, durable account system or live database catalog in the current implementation.

The current catalog source of truth is the in-memory fixture in [src/data/catalog.ts](src/data/catalog.ts). The current contact and cake forms send email through server functions in [src/lib/mail.functions.ts](src/lib/mail.functions.ts).

## 2. Technology stack

### Languages and platform

- **TypeScript**: application and configuration code. Strict compiler settings are defined in [tsconfig.json](tsconfig.json).
- **TSX/React JSX**: React components and route pages.
- **JavaScript**: ESLint configuration in [eslint.config.js](eslint.config.js).
- **CSS**: shared styling and Tailwind CSS utility classes in [src/styles.css](src/styles.css) and component markup.
- **HTML**: generated by the React/TanStack Start shell and the fallback server error page.
- **Node.js APIs**: used by build configuration and server-side code, including `process.env`, `fs` and `path`.
- **Web platform APIs**: `fetch`, `Request`, `Response`, `FormData`, `IntersectionObserver`, `localStorage`, DOM events and browser history.

### Application frameworks

- **React 19**: component model and client-side interaction state.
- **TanStack Start**: full-stack React framework, SSR request handling, server functions and server middleware.
- **TanStack Router**: file-based, type-safe routing, route loaders, route search validation, route metadata and nested layouts.
- **TanStack React Query**: a `QueryClient` is created in [src/router.tsx](src/router.tsx) and provided to the route tree. Current catalog pages mostly read fixture data synchronously; the query client is ready for future server-backed data.
- **Vite**: development server and build orchestration.
- **Nitro**: the server/build target used by the TanStack preset. [vite.config.ts](vite.config.ts) points the generated server at [src/server.ts](src/server.ts).
- **Tailwind CSS v4**: utility-first styling through the Vite/TanStack preset and shared CSS.
- **Radix UI**: accessible headless UI primitives wrapped in [src/components/ui](src/components/ui).
- **Zod**: server-side form input validation in [src/lib/mail.functions.ts](src/lib/mail.functions.ts).
- **Lucide React**: icons used by shared navigation and footer components.

### Build, lint and formatting tools

The scripts are declared in [package.json](package.json):

| Command | Purpose |
| --- | --- |
| `npm run dev` | Start the Vite development server. |
| `npm run build` | Create a production build. |
| `npm run build:dev` | Build using development mode. |
| `npm run preview` | Serve a built application locally. |
| `npm run lint` | Run ESLint over the project. |
| `npm run format` | Format files with Prettier. |

The repository currently has no dedicated test script. A production change should therefore be checked with at least `npm run lint` and `npm run build`, plus manual route checks for the affected behavior.

The existing mail functions still build and run, but a future TanStack Start upgrade should migrate these calls to the newer `.validator()` API as a focused change, followed by form and CSRF verification.

## 3. High-level architecture

```text
Browser request
    |
    v
Nitro / TanStack Start runtime
    |
    +--> src/server.ts
    |       +--> lazy-load generated TanStack server entry
    |       +--> normalize swallowed SSR 500 responses
    |       +--> return HTML error page when needed
    |
    +--> src/start.ts middleware
    |       +--> error middleware
    |       +--> CSRF middleware for server functions
    |
    +--> src/router.tsx
            +--> generated route tree: src/routeTree.gen.ts
                    +--> root layout: src/routes/__root.tsx
                            +--> SiteHeader
                            +--> nested route component
                            +--> SiteFooter

Shared route data and behavior:

src/data/catalog.ts
    +--> route pages
    +--> ProductCard / ProductGallery
    +--> SiteHeader search suggestions
    +--> retail and wholesale filtering

Server-only interaction:

Contact or cake form
    -> useServerFn(...)
    -> createServerFn in src/lib/mail.functions.ts
    -> Zod validation
    -> RESEND_API_KEY from server environment
    -> Resend HTTP API
```

The important ownership rules are:

1. [src/routes](src/routes) owns URL-level behavior and page composition.
2. [src/components](src/components) owns reusable visual and interaction behavior.
3. [src/data/catalog.ts](src/data/catalog.ts) owns the current catalog domain model and fixture data.
4. [src/lib](src/lib) owns cross-cutting logic, server functions, mode state, search parsing and error handling.
5. [src/server.ts](src/server.ts) owns the final HTTP fetch boundary and catastrophic SSR fallback.
6. [src/start.ts](src/start.ts) owns TanStack Start request middleware.
7. [src/routeTree.gen.ts](src/routeTree.gen.ts) is generated output and must not be edited by hand.

## 5. How a request runs through the project

### Initial page request / SSR

1. Vite/Nitro receives an HTTP request.
2. The configured server entry points to [src/server.ts](src/server.ts).
3. `server.ts` lazy-loads `@tanstack/react-start/server-entry` once and caches the promise.
4. The generated Start entry uses [src/start.ts](src/start.ts) and the router configuration.
5. TanStack Start runs request middleware. The error middleware converts unexpected exceptions into a 500 HTML page while preserving framework status errors. CSRF middleware protects server functions.
6. TanStack Router matches the URL against [src/routeTree.gen.ts](src/routeTree.gen.ts).
7. The root route renders the document shell, `QueryClientProvider`, `ModeProvider`, header, loading screen and footer.
8. The matching child route renders inside the root `<Outlet />`.
9. Route `loader` functions run for dynamic department/product routes before their components consume `Route.useLoaderData()`.
10. Route `head` functions produce title, description, social metadata and, for FAQ, structured data.
11. The response is returned to the browser with the SSR HTML and client scripts.

### Client navigation

1. A TanStack `Link` or `useNavigate` call updates the URL without a full browser reload.
2. TanStack Router matches the new route and runs any required loader/search validation.
3. The root shell remains mounted; only the nested route content changes.
4. React updates the route component and shared state.
5. Scroll restoration and route preloading are controlled by [src/router.tsx](src/router.tsx).

### Route communication

Routes do not directly call each other as functions. They communicate through:

- Typed TanStack `Link` and `useNavigate` calls.
- URL path parameters, such as `productId` and `slug`.
- URL search parameters validated by `parseCatalogSearch`.
- Shared catalog functions and types from [src/data/catalog.ts](src/data/catalog.ts).
- Shared root context, especially the React Query client.
- Shared React context, especially `ModeProvider` and `useMode`.
- Shared components such as `ProductCard`, `ProductGrid`, `Reveal` and `HeroSlideshow`.

The retail and wholesale product detail routes intentionally share the same product identity (`product.id`) but present different commercial fields. Do not assume a retail route can safely display wholesale pricing or that a wholesale route can use retail pricing logic.

### Form/server-function flow

1. [src/routes/contact.tsx](src/routes/contact.tsx) or [src/routes/bakery.tsx](src/routes/bakery.tsx) reads browser form values into a plain object.
2. `useServerFn` creates a client-safe caller for the server function.
3. The TanStack Start server function receives the request and CSRF middleware checks it.
4. Zod validates and trims the input against the route-specific schema.
5. `sendEmail` reads `process.env.RESEND_API_KEY` on the server only.
6. The server sends an HTTPS request to Resend and returns `{ ok: true }` on success.
7. The route updates its local `busy`, `sent` and `error` state.

Never import the mail implementation into a browser-only utility or expose `RESEND_API_KEY` through a `VITE_*` variable.

## 6. Data model and current data flow

`catalog.ts` currently contains:

- `Department`: slug, display name, description and subcategories.
- `Product`: stable ID, name, brand, department, subcategory, pack data, retail prices, promotional fields, stock, images, descriptions, nutrition/allergens and wholesale fields.
- Store metadata: address, hours, phone, email, map query and counter times.
- Derived lists such as offers, bakery items, deli items and fresh-today content.
- Lookup and display helpers such as `productById`, `departmentBySlug`, `productsByDepartment`, `hasOffer`, `effectivePrice`, `formatKES` and stock labels.

The safe future replacement is to preserve these domain types and helper contracts while moving the read implementation behind a server-side catalog service. The browser must never connect directly to the company database.

## 7. Safe change and upgrade procedures

### Before editing

1. Read the owning route/component and its nearest shared dependency.
2. Determine whether the change is client-side, server-side, generated, data-contract, styling or infrastructure work.
3. Search for all usages of any exported type, helper or component being changed.
4. Check whether the behavior is shared by retail and wholesale mode.
5. Check whether the route has a loader, search validator, metadata function or server function.
6. Avoid editing unrelated dirty-worktree changes.

### When changing routes

- Create or rename files according to TanStack file-route conventions.
- Use `createFileRoute("/exact/path")` with the path matching the generated route contract.
- Use `$param` filenames for dynamic segments.
- Use `wholesale.tsx` as the parent layout for wholesale child routes and preserve its `<Outlet />`.
- Do not edit [src/routeTree.gen.ts](src/routeTree.gen.ts); let the TanStack plugin regenerate it.
- After adding or renaming a route, run the development server or production build so the route tree is regenerated and type errors surface.
- Add route metadata and explicit not-found behavior for user-controlled IDs/slugs.

### When changing catalog data

- Preserve stable product IDs. Links, suggestions, related products and route params depend on them.
- Preserve department slugs unless a redirect/migration plan exists.
- Keep retail price fields separate from wholesale fields.
- Keep `promoPrice` optional and use existing helpers for effective pricing.
- Keep image imports valid and test every affected card/detail route.
- Update both retail and wholesale views when changing `Product`.
- If moving to a database, validate and normalize external data before it reaches the UI. Do not replace a valid published snapshot with a partial import.

### When changing shared components or providers

- Treat [src/routes/__root.tsx](src/routes/__root.tsx), `SiteHeader`, `SiteFooter`, `ProductCard`, `ProductGrid`, `ModeProvider` and `catalog.ts` as high-blast-radius files.
- Preserve `QueryClientProvider`, `ModeProvider`, `<Outlet />`, `<Scripts />`, not-found handling and error handling in the root route.
- Test both `retail` and `wholesale` mode after changing product cards, header navigation or mode state.
- Do not move server-only imports into components that render in the browser.
- Keep generic UI primitives free of catalog-specific business rules.

### When changing server code

- Keep secrets in server environment variables. Only `VITE_*` values are intended for browser exposure.
- Preserve CSRF protection for all `createServerFn` handlers.
- Validate every server input with Zod or an equivalent server-side validator.
- Keep email HTML escaped; never interpolate raw user input into markup.
- Preserve the `server.ts` fallback path and the h3 swallowed-error normalization unless the framework version and behavior have been verified.
- Avoid logging submitted personal data or secrets.
- Set timeouts, error handling and stale-data behavior before adding external APIs or a database.

### When changing dependencies or frameworks

1. Read the release notes for React, TanStack Start, TanStack Router, Vite, Nitro and the relevant adapter.
2. Upgrade one framework family at a time where practical.
3. Update the lockfile with the package manager used by the repository.
4. Run `npm run lint` and `npm run build`.
5. Check SSR routes, dynamic not-found routes, form submissions, mode switching, search query state and production preview.
6. Check generated route output after router/plugin upgrades.
7. Do not manually add plugins already installed by `@lovable.dev/vite-tanstack-config`; duplicate TanStack, React, Tailwind or Nitro plugins can break the build.

## 8. Verification checklist

For a normal feature change:

```text
1. npm run lint
2. npm run build
3. Start the dev server with npm run dev
4. Check the changed route directly in the browser
5. Check one linked route and one dynamic/not-found case if routing changed
6. Check retail and wholesale mode if product/navigation code changed
7. Check the browser console and server logs
```

Minimum route smoke checks:

- `/`
- `/catalog`
- `/offers`
- `/departments/fresh-produce`
- `/departments/not-a-real-department`
- `/product/hass-avocado-3pk`
- `/product/not-a-real-product`
- `/bakery`
- `/contact`
- `/wholesale`
- `/wholesale/catalog`
- `/wholesale/hass-avocado-3pk`
- `/admin`

For form changes, verify success, validation failure, missing `RESEND_API_KEY`, CSRF rejection behavior and server error presentation. Use a safe test recipient/configuration; never commit credentials.

## 9. Known limitations and next architectural steps

The current implementation is a polished catalog frontend, not a complete commerce backend. The next major changes should be designed as explicit boundaries:

1. **Live catalog**: add a server-side repository/API and keep the existing `Product` contract stable while replacing fixture reads.
2. **Synchronization**: stage, validate and publish complete snapshots from the company source. Record import status and last successful sync time.
3. **Caching**: add controlled server-side caching, timeouts and a stale-data policy.
4. **Account interest**: replace the local `/login` acknowledgement with a validated, deduplicated, consent-aware server function and durable storage.
5. **Admin security**: authenticate and authorize `/admin` before exposing operational data or mutation controls.
6. **Wholesale quotes**: add a server-side quote workflow without leaking prices or coupling it to retail checkout.
7. **Checkout**: introduce cart, payment and order state as a separate bounded domain. Do not retrofit checkout behavior into the current catalog helpers casually.
8. **Tests and observability**: add route/component tests, catalog contract tests, import tests, server-function tests and monitoring before production integrations are enabled.

The safest guiding principle is to preserve the current boundaries: routes compose pages, components render reusable behavior, catalog helpers define domain rules, server functions handle secrets and external side effects, and the server entry owns HTTP-level failure recovery.
